# History-compatibility check

A local harness that proves the Rust port can read real, years-old
`.multiverse/` history — not just the synthetic scenarios `conformance/`'s
sibling harness constructs. It has three parts:

- **`collect.sh`** — snapshots the file families this lane's brief names
  (routing log + index/fingerprint, task directories, activity cursors,
  worktree task dirs, `handoff`, and the three fleet-level stores
  breaker/seat/gauge) from real project `.multiverse/` directories into a
  local, gitignored `corpus/`. Read-only against its sources; never
  commits real data (see `.gitignore` in this directory).
- **`fixtures/`** — small, committed, *synthetic* `multiverse-state/` trees
  (see "What a corpus root looks like" for why that name, not `.multiverse/`)
  that mimic every documented format variant without containing any real
  project's data: pre-rename old role names, the pre-versioned
  (no `v=`/`seq=`/`crc32=`) routing.log envelope alongside the current
  `v=1` one, a deliberately damaged `crc32=`, and the other edge cases
  `spec-on-disk-contract.md` and `audit-mail-backlog-board-disk.md` call
  out. Regenerated by `fixtures/generate.py` — see that file's own header
  before hand-editing anything under `fixtures/`.
- **`runner/`** — a Rust binary that walks a corpus (real or synthetic)
  and reports every record that fails to parse, by file and line, plus a
  count of every format variant it recognized.

## Why `runner/` is its own Cargo workspace

The runner remains an independent workspace rather than an eighth member
of the shared root manifest. Run its checks separately: root workspace
builds and tests do not include it.

The fleet checks now deserialize entries using `mv-state::breaker_store`,
`mv-state::gauge`, and `mv-state::seatstate_store`'s production types. This
keeps optional/null fields, known-field types, and unknown-field tolerance
aligned with production. The runner reports each malformed entry rather
than calling the fail-open `load` functions, which replace an unparseable
store with an empty map and would hide planted defects.

The other `runner/src/*.rs` checks (`activity.rs`, `routing_log.rs`,
`tasks.rs`, `worktrees.rs`) encode their contracts locally, and each was
evaluated against its `mv-state` counterpart and deliberately *not*
migrated — see each file's own module doc for the specific mismatch found
(field-order tolerance, retry-for-live-races, no equivalent function to
call, and so on). The shared reason: those modules are production
readers, built to tolerate drift so a live fleet never crashes on it; this
runner is the independent oracle checking that the on-disk data has no
drift to tolerate, so reusing their lenient parsing would quietly narrow
what counts as a finding.

## Quick start

```sh
# One-time, local, against real projects (adjust paths/state dir to your
# own fleet). Read-only; writes nothing back to any of these directories.
./collect.sh --state-dir ~/.config/multiverse --out corpus \
    ~/Code/Project1 ~/Code/Project2 ...

# Build and run against the collected corpus, or the committed fixtures,
# or both in one pass:
(cd runner && cargo build --locked)
runner/target/debug/mv-history-runner corpus fixtures
```

Exit code is nonzero whenever the findings list is non-empty. Running
against `fixtures/` alone is *expected* to exit nonzero: it contains six
history defects and sixteen malformed fleet entries. The tests also pass
three nested corpus roots explicitly: `fixtures/fleet-tolerant/`,
`fixtures/fleet-invalid-json/`, and `fixtures/fleet-invalid-top-level/`.
These add zero, three, and three findings respectively, for 28 total.
The tests pin each damaged entry/file as well as the total count.

Run the complete fixture checks from the repository root:

```sh
cargo test --manifest-path conformance/history/runner/Cargo.toml --locked
cargo fmt --manifest-path conformance/history/runner/Cargo.toml -- --check
cargo clippy --manifest-path conformance/history/runner/Cargo.toml --all-targets --locked -- -D warnings
```

`fixtures/fleet-tolerant/` covers legacy breaker entries without `open`
and partial gauges without probe metadata. It also covers
empty entries, null optional fields, partial seat flags, both secondary
window naming conventions, and unknown fields. Running the binary against
this root alone must exit zero with **0 findings**. Tolerant history scenarios
(old role names, both envelope eras, unsanctioned files, non-terminal status,
and corrupt `.lastseen`/`.lastack`) must likewise produce no findings.

## What a corpus root looks like

Both `collect.sh --out <dir>` and `fixtures/` produce the same shape, so
`runner` treats them identically: a directory of subdirectories, each
either

- a **project**: `<name>/multiverse-state/{routing.log, routing.log.index,
  routing.log.index.fp, activity.cursor, activity.lastseen,
  activity.lastack, handoff, tasks/<id>/..., worktrees/<id>/multiverse-state/tasks/<id>/...}`
  (any of these may be absent — a scenario only needs the files it's
  testing), or
- the fleet state dir, named exactly **`fleet-state`**:
  `fleet-state/{breaker-state.json, seat-state.json, gauge-state.json}`.

The corpus-internal directory is named `multiverse-state/`, **not**
`.multiverse/`, even though every byte in it is a snapshot of some real
project's actual `.multiverse/`. This is deliberate: this machine's
`.git/info/exclude` carries an unanchored `.multiverse/` rule (any depth),
there to stop a dispatched task's own `.multiverse/` state from ever being
committed. A committed fixture tree built to mirror the real layout
byte-for-byte would use that same name and be silently swallowed by that
same rule — found live while committing the first version of `fixtures/`,
where `git add -n` showed every fixture file *except* the ones under a
`.multiverse/` path. Forcing past it (`git add -f`) was not an option —
this lane's own brief forbids exactly that, for exactly this class of
mistake. Renaming the corpus's own directory sidesteps the rule instead of
fighting it; `collect.sh` still *reads* from each real project's actual
`.multiverse/`, only the destination name differs from its source.

`collect.sh` deliberately does **not** copy a worktree's actual git
checkout — a large `api-service` project's `worktrees/` alone runs to
3.7 GB on the live fleet across 39 lanes, and none of those bytes are read by any
history-compatibility check. Only the worktree directory's name and its
nested `multiverse-state/tasks/<id>/` (the same sanctioned-file whitelist
as a project's own `tasks/<id>/`) are captured. A task directory's
unsanctioned files (scratch scripts, diffs — real history has plenty, per
`spec-on-disk-contract.md` §B) are recorded as zero-byte placeholders of
the same name, so "ignore files I don't recognize" is still exercised
without the corpus carrying arbitrary bytes.

## What `runner` actually checks

| File family | Rule enforced |
|---|---|
| `routing.log` | Tab-separated envelope, both the legacy (no `v=`/`seq=`/`crc32=`) and current `v=1` shapes; `crc32=` verified against the exact bytes preceding it (confirmed against live on-disk records, not just the spec prose — see `runner/src/routing_log.rs`'s module doc); `role=` on `event=dispatch`/`event=result` checked against the closed old+new name set, free-text on `event=backlog`; `event=backlog state=asked` `options=`/`recommendation=` validated per the audit's P1 correction |
| `tasks/<id>/status` | Exact-match `done`/`blocked`/`failed` only; anything else (`donedone`, empty, invalid UTF-8) is a counted *tolerated* variant, never a finding — matching `_read_task_status`'s own fold-to-absent behavior |
| `tasks/<id>/retire` | `<task-id> <40-hex sha>` per line |
| `tasks/<id>/*` (anything else) | Tolerated, counted, never read as a sanctioned file |
| `activity.cursor` | Fail-closed: malformed, negative, or **ahead of `routing.log`'s own high-water `seq`** (a log-reset/replacement generation mismatch, not an empty inbox — the audit's P1 correction) |
| `activity.lastseen` / `activity.lastack` | Tolerant — a malformed file is a counted variant, never a finding |
| `worktrees/<id>/` | Directory name is task-id-shaped; every nested task dir (if present) is checked like any other task dir. A nested id differing from the worktree's own is counted (adoption — a later follow-up task reusing the checkout), never flagged — real data showed this is the common case, not corruption |
| `breaker-state.json` | Each pool is an object deserializable as `BreakerEntry`; `open` and other known fields are optional/null, with production types when non-null; unknown fields are accepted |
| `seat-state.json` | Each seat is an object deserializable as `SeatEntry`; `cap` is an optional/null `u32`, `lend`/`prefer` are optional/null booleans; unknown fields are accepted |
| `gauge-state.json` | Each pool is an object deserializable as `GaugeEntry`; all known fields are optional/null and checked by production types when non-null; unknown fields (including legacy `secondary_*`) are accepted |

## What this does not cover

- **Branch-naming and git-ref checks for worktrees** (the
  `multiverse/YYYYMMDD-<role>-<hex>` convention `mv-state::worktrees`'s doc
  comment names). `collect.sh` deliberately never copies the git checkout,
  so there is no ref to check from a snapshot; this needs either a
  metadata sidecar added to `collect.sh`'s output or, once
  `mv-state::worktrees` exists, running it directly against a live
  worktree rather than a corpus snapshot.
- **`roster.toml`**, `finish-nudge-memory.json` and its
  non-atomic-write siblings, `orchestrator-pass`, `evidence/`, and every
  other file `spec-on-disk-contract.md` §A/§B documents but this lane's
  brief does not name in its reader list (routing log, tasks, backlog,
  activity, worktrees, breaker/gauge/seat). Not collected, not checked.
- **Mail and backlog as file formats.** Per
  `spec-on-disk-contract.md` §B ("one ledger, not two"), both live as
  record kinds inside `routing.log`, not separate files — `runner`
  checks them there (`event=message`/`event=backlog`), not as distinct
  file-family checks.
- **The old→new role-name mapping** used to validate `event=dispatch`/
  `event=result`'s `role=` field is *inferred* from each role's stated
  purpose in `docs/roles.md` (oracle→Seer, librarian→Archivist,
  designer→Artisan, observer→Watcher), not sourced from a committed
  mapping table — `crates/mv-config/src/roles.rs` is itself still a
  doc-only stub. If the real mapping lands differently, update
  `runner/src/routing_log.rs`'s `NEW_ROLES`/old↔new pairing.
- **Production reader integration outside fleet stores.** Only the three
  fleet-store entry types are reused; the other history checks remain local.

## Status

Run once, locally, read-only, against seven live projects in a sample
fleet (for example, `/home/user/code/{demo-app,api-service,...}`) and the
fleet config-state dir, 2026-11-02: **3 findings**, all three in
`fleet-state`'s JSON stores. These were checker false positives from
requiring fields that production readers accept as optional — zero
findings anywhere in `routing.log`,
`tasks/`, `activity.*`, or `worktrees/` across roughly 71k routing.log
lines and 8.5k task directories. Two corrections this run forced *in this
checker itself*, not in the data (see `runner/src/tasks.rs` and
`worktrees.rs`'s inline comments for the detail): a worktree's nested task
dir commonly holds a different id than the worktree itself (adoption, not
corruption — the first run against real data flagged 45 of these as false
positives before the fix), and `retire` lines name a full `multiverse/`
branch ref, not a bare task id. The inline comments describe both
compatibility corrections.

The fleet-store correction now reports **0 findings** on synthetic versions
of the field-omission variants, plus optional/null/unknown-field cases.
Malformed JSON, non-object stores and entries, wrong known-field types,
and out-of-range unsigned integers retain planted-defect coverage. This
correction was checked against committed synthetic fixtures only; the live
corpus was not recollected or rerun for this task.
